## 二、F407 里现在跑的是什么

### 2.1 已不是 GoodDog 了

| | 烧录前 | 现在 |
|---|---|---|
| 固件 | GoodDog（交付包 9-28 那版，34 996 B） | **新应用层固件 fw407（20 756 B）** |
| 视觉链路 | USART3 / PD8 / PD9 | **USART1 / PA9 / PA10**，115200 |
| 协议 | 粘连式 `PING` / `PS<speed>` / `TA<deg>` / `FIRE<ms>`（V1.1） | **`@T,seq,CLS,conf,x,y,w,h,flags*crc`** |
| 状态机 | 无 | INIT → IDLE → AUTO / SAFE_STOP / FAULT |
| 看门狗 | — | IWDG 500 ms，唯一喂狗点在 `safety_tick_1ms()` |

> 协议换了是**关键变化**：老的 `PING/PS/TA/FIRE` 那套现在是无效的，
> 与新固件对不上。新协议是 ASCII 行帧，CRC-8（poly 0x07）校验，
> 两侧算法已经用 5 组测试向量交叉验证过（含 `@T,104,WEED,0.88,...` → CRC `0x6C`）。

### 2.2 运行时实测

```
s_state     = 1 (IDLE)         fault = 0 (NONE)
uptime      = 60994 → 61502 ms 连续增长（脱机、无调试器介入）
streak      = 0                三路心跳 [61501, 61501, 61501] 全部新鲜
USART1_CR1  = 0x0000201C       UE/TE/RE/IDLEIE 全开
USART1_BRR  = 0x000002D9       115200 @ 84 MHz APB2
TIM3/TIM4   = 0x00000081       CEN=ON（舵机 50 Hz / 电机 PWM）
ul_dma_err  = 0
```

**上电姿态是安全的**：`SYS_IDLE` 下 `motor_enable(false)`、两路 PWM 占空比为 0、
`motion_request_stop()`。上电不会驱动任何执行器。

### 2.3 第一次烧录踩的坑

刚烧完是"每 500 ms 复位一次、串口零输出"。查出来是 6 个叠在一起的固件缺陷
（FAULT 自锁复位环、`HB_CONTROL` 从未被喂、视觉心跳绑在收帧上、时基不同源、
初始化不进 IDLE、DMA 重复启动）。

完整分析见 **[F407固件构建与烧录.md](F407固件构建与烧录.md) 第四节**。
修完后 60 秒生存测试通过。

## 三、两颗芯片为什么还没在对话

**因为线还没接。** 这不是软件问题 —— 而且现在软件侧已经全部验证过了。

### 3.1 两侧其实都已经就绪

| 侧 | 状态 |
|---|---|
| F407 | USART1 已使能（`UE=ON, TE=ON, RE=ON, IDLEIE=ON, DMAR=ON`），DMA 循环接收就位 |
| OpenMV | `vision_node/` 已部署到 `/flash` 并跑起来了：`detector=blob`、`infer≈21ms`、每 50ms 发一帧 `@T,...` |

但 F407 侧 `ul_bytes_rx = 0`、`vp_frames_ok = 0` —— 一个字节都没进来。

### 3.2 两条证据说明"软件侧没问题，只差物理连接"

**证据一：PD8/PD9 也没有数据。**
老 GoodDog 固件用的是 USART3（PD8/PD9）。用调试器直接配置 RCC/GPIOD/USART3
（固件从不碰这三个），轮询 5 秒，`RXNE/ORE` 命中 **0 次**。
说明机箱里现成的线**并没有接在老端口上**，不存在"改个串口号就能通"的捷径。

**证据二：把一帧直接注入 F407 的环形缓冲，解析链路立刻工作。**
`_toolchain/inject_frame_f407.py` 绕过物理层，把
`@T,104,WEED,0.88,52,131,60,71,0*6C\n` 写进 `s_ring` 并按驱动的方式推进 `head`：

```
[注入前] frames_ok=0  err_crc=0
[注入后] frames_ok=1  err_crc=0  err_field=0
=> PASS —— 从环形缓冲到目标发布的整条链是通的
```

**剩下的唯一缺口就是 PA9/PA10 与 P4/P5 之间那两根线。**

### 3.3 ⚠️ 协议换代了，别用错 OpenMV 固件

这条比接线更容易踩：仓库里有两套互不兼容的 OpenMV 固件。

| 固件 | 协议 | 配套 F407 |
|---|---|---|
| `openmv/weeder.py` / `main.py` / `main_diag.py` | V1.1 粘连式 `PING`/`PS`/`TA`/`FIRE` | 老 GoodDog（USART3） |
| **`openmv/vision_node/`** | **`@T,seq,cls,conf,cx,cy,w,h,dist*crc`** | **新应用层固件（USART1）** |

用错的表现极其隐蔽：串口上有波形、F407 也不报错，只是 `vp_frames_ok` 永远 0。

详见 [openmv/README_两代架构.md](../openmv/README_两代架构.md)。

### 接线表

| F407 | 方向 | OpenMV |
|---|---|---|
| **PA9** (USART1_TX) | → | **P5** (UART3 RX) |
| **PA10** (USART1_RX) | ← | **P4** (UART3 TX) |
| GND | — | GND |

> ⚠️ 老固件用的是 PD8/PD9，机箱里现成的线如果是接在那两个脚上，**要挪到 PA9/PA10**。
> ⚠️ TX/RX 必须交叉，且必须共地。

## 五、下一步

1. **接线**：F407 `PA9` → OpenMV `P5`，F407 `PA10` → OpenMV `P4`，`GND` ↔ `GND`
   （TX/RX 必须交叉，必须共地）
2. **验收链路**：
   ```bash
   python _toolchain/verify_f407.py      # 看 ul_bytes_rx / vp_frames_ok 是否增长
   ```
   增长即链路通。OpenMV 侧在 COM4 上持续打印 `infer=... det=(N,0)`。
3. **确认目标帧内容**：`vp_frames_ok` 增长但 `s_state` 仍为 IDLE 是正常的 ——
   进 AUTO 还需要 `safety_request_auto(true)`，目前没有实现下行命令通道。
4. **上电池**：链路通了以后再脱开 ST-Link 跑一次
   `python _toolchain/soak_f407.py 60`，确认整机自主运行。

> OpenMV 目前跑的是 `blob` 色块模式（无模型），只用于验证链路。
> 真正的杂草识别需要 FOMO 检测模型 —— 仓库里的 `*_int8.tflite` 是分类模型，
> 不能直接替换（接口不同：一个输出单标签，一个要输出多个检测框）。
