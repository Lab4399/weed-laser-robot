## 三、依赖关系

```
app_main.c  ← 启动流程，依赖全部模块
│
├─→ app_config.h        全局参数（被所有模块 include）
├─→ app_tasks.c         创建 4 个任务
├─→ uart_link.c ──→ HAL      USART1 + DMA2
├─→ motor.c     ──→ HAL      TIM4 CH1~4 @ PB6~PB9
├─→ servo.c     ──→ HAL      TIM3 CH1/2 @ PA6/PA7
├─→ motion.c    ──→ motor.h  差速解算
├─→ safety.c    ──→ motor.h + servo.h + motion.h   （安全闸，能直接断执行器）
├─→ param.c     ──→ HAL      读写 Flash sector 10/11
└─→ vision_proto.c           ★ 只依赖 app_config.h，不依赖 HAL
```

### 值得注意的结构特点

**1. `vision_proto.c` 与硬件解耦**

它只 `#include "vision_proto.h"` 和 `app_config.h`，**不碰任何 HAL**。
所以能在 PC 上直接编译测试——`tests/host_proto_test.c` 就是干这个的（10920 B）。

这意味着：**协议层的验证不需要烧板子**，在 PC 上跑就行。这是很高的工程水准。

**2. `safety.c` 能直接操作执行器**

它 include 了 `motor.h` / `servo.h` / `motion.h`，可以绕过上层直接断输出。
这是"安全闸"的正确做法——不依赖业务逻辑配合。

**3. 调试输出走 SWO/ITM，不走主链路 UART**

`app_tasks.c` 里 `dbg_puts()` 写 `0xE0000000`（ITM 端口），理由写在注释里：

> 主链路 UART 已被 OpenMV 占用，插打印会污染协议流；双向都有数据时示波器抓包会难以判读

这个细节说明作者踩过坑。

## 四、启动顺序（注释明确"不可随意调整"）

```
① vision_proto_selftest()   协议自检 —— 挡在启动阶段，不一致时现象极难反推
② param_init() / param_get() 参数载入 —— 必须在运动模块初始化之前
③ uart_link_init() / motor_init() / servo_init() / motion_init()
④ motion_set_params() / servo_set_us()
⑤ safety_init()             依赖已初始化的电机与运动模块
⑥ HAL_IWDG 启动             最后启动，否则前面耗时步骤会被看门狗咬
⑦ app_tasks_start()         创建任务
```

对应 `app_main.c` 第 58 / 67 / 76 / 79-83 / 86-87 / 92 / 113 行。

## 五、运行时状态

### FreeRTOS 任务（实际创建 4 个）

| 任务 | 优先级 | 栈 | 职责 |
| --- | --- | --- | --- |
| `safety` | 10 | 512 B | 最高优先级，状态机与看门狗 |
| `motion` | 8 | 1024 B | 运动控制，100 Hz |
| `vision` | 6 | 1024 B | 协议解析与视觉数据处理 |
| `diag` | 2 | 768 B | 诊断输出 |

> 注意：`app_config.h` 里定义了 5 组 `TASK_STACK_*` / `TASK_PRIO_*`
> （SAFETY / CONTROL / VISION / MOTION / PARAM），但实际创建时
> `motion` 用的是 `TASK_PRIO_CONTROL`，`param` 对应的任务改名为 `diag`。
> **实际是 4 个任务，不是 5 个。**

### 系统状态机（5 态）

| 状态 | 含义 |
| --- | --- |
| `SYS_INIT` | 上电自检中，**输出全关** |
| `SYS_IDLE` | 待机/手动模式，**电机使能关闭** |
| `SYS_AUTO` | 自动跟踪作业 |
| `SYS_SAFE_STOP` | 安全停机：**切断功率，保留通信** |
| `SYS_FAULT` | 故障锁死：**仅人工复位可解除** |

两个设计要点：

- `SYS_SAFE_STOP` 不是断电，而是断功率但保持串口活着，
  这样上位机能知道"我还活着，只是不敢动"。
- `SYS_FAULT` 是锁死的，必须人工复位——防止故障条件消失后系统自动恢复运行，
  把操作员晾在一边。

### 故障码（7 种 + NONE）

枚举定义为 `FAULT_NONE = 0` 起，共 8 项，其中实际故障 7 种：

| 故障码 | 触发条件 |
| --- | --- |
| `FAULT_LINK_TIMEOUT` | 视觉链路持续无有效帧 |
| `FAULT_CRC_BURST` | CRC 错误率超限，疑似线材/波特率问题 |
| `FAULT_ESTOP` | 急停输入触发 |
| `FAULT_TASK_STALL` | 关键任务心跳超时 |
| `FAULT_PARAM_LOST` | 参数双备份全损，已回退出厂值 |
| `FAULT_IWDG_REPEAT` | 连续多次看门狗复位 |
| `FAULT_MOTOR_DISABLED` | 驱动器使能被意外关闭 |

这 7 条覆盖了：链路、数据质量、人为、软件卡死、存储、复位循环、硬件使能——
基本是嵌入式系统会遇到的失效全集。

## 七、与 OpenMV 侧的对接点

| 项 | F407 侧 | OpenMV 侧 | 一致 |
| --- | --- | --- | --- |
| 物理链路 | USART1 @ PA9(TX)/PA10(RX) | UART3 @ P4(TX)/P5(RX) | 需接线 P4→PA10、P5→PA9 |
| 波特率 | 115200 | 115200 | ✓ |
| 帧格式 | `@T,SEQ,CLASS,CONF,CX,CY,W,H,DIST*HH` | 同 | ✓ |
| CRC | CRC-8 poly=0x07 init=0x00 | 同 | ✓ |
| 图像宽度 | `LINK_IMG_WIDTH` = 320 | `IMAGE_WIDTH` = 320 | ✓ |
| 超时 | `LINK_TIMEOUT_MS` = 600 / DEGRADE 900 | 心跳 50ms、推理 200ms | 见下 |
| 自检 | `vision_proto_selftest()` | `FrameBuilder.selftest()` | 双方都有 |

**超时约束**：F407 要求 `LINK_TIMEOUT_MS > 单帧推理最坏耗时 × 1.5`，
即 **推理最坏耗时必须 < 400 ms**。OpenMV 的 `main.py` 已在打印 `infer_ms_max`，
需要实测确认。

| 1 | `host_proto_test.c` 是否已在 PC 上跑过 | 若跑过，协议层可以认为已验证；若没跑，这是成本最低的验证方式 |

## 九、一句话总结

> 这套固件是**分层清晰、安全优先**的结构：
> 协议层与硬件解耦可离线测试，安全闸能直接断执行器，
> 7 个故障码覆盖主要失效模式，Flash/RAM 余量都在 95% 以上。
> 20 KB 的体量对这个规模是合理的，不是残缺构建。
