烧进 STM32F407ZGTx，并验证它能脱机独立运行。

### 3.1 烧录

```bash
cd E:/PlantDiseaseProject/_f407build/fw/build
pyocd flash -t stm32f407zgtx --erase sector fw407.elf
```

> 用 `chip_erase` 时 pyocd 的闪存算法在目标 RAM 里会触发 HardFault，

## 四、本次修掉的 6 个固件缺陷

上板后第一次运行是 **每 500 ms 复位一次、串口一句输出都没有**。
逐个查下来是 6 个独立缺陷叠在一起，任何一个单独存在都会让机器"上电没反应"。

### 缺陷 1（致命）：FAULT 状态主动停喂狗 → 自锁复位环

```c
/* 修改前：safety.c */
if (s_state != SYS_FAULT) {
    HAL_IWDG_Refresh(&hiwdg);     /* 故障时故意不喂，指望 IWDG 复位 */
}
```

原意是"故障就让看门狗复位"，但复位后 `safety_init()` 读到
`.noinit` 里的 `s_iwdg_reset_streak` 超限，又直接进 FAULT —— 形成闭环：

```
FAULT → 不喂狗 → 500 ms 后复位 → streak++ → 开机又 FAULT → 再复位 …
```

实测 `s_iwdg_reset_streak = 75`，即已经空转了 75 次。因为计数存在 RAM 的
`.noinit` 段里，**只要不断电就永远存在**。

**修复**：只要 1 ms 任务还在跑就喂狗，不区分状态。看门狗的职责是发现
"调度器/任务死了"，不是惩罚一个已经锁存的故障。故障态继续喂狗，设备才能
停在 FAULT 里保持可诊断、可远程清除。

配套加了第 7 条：`s_uptime_ms >= 10 s` 时把 `streak` 清零。语义变成
"连续多少次没能正常跑起来"——真正起不来的固件永远跑不到 10 秒，保护不失效；
能跑满 10 秒就说明之前的复位是历史问题。

### 缺陷 2（致命）：`HB_CONTROL` 从头到尾没有任何人喂

`safety_tick_1ms()` 遍历 3 个心跳，超时窗口 `200 ms × 10 = 2 s`。
但全工程只有 `HB_VISION` 和 `HB_MOTION` 有 `safety_heartbeat()` 调用，
`HB_CONTROL` 永远是 0 —— **开机 2 秒后必然 `FAULT_TASK_STALL`**。

**修复**：控制任务同时承担"控制律"与"运动输出"，两个心跳都喂。

### 缺陷 3（致命）：视觉心跳只在"收到有效帧"时才喂

```c
if (vision_proto_feed(...)) {
    safety_on_valid_frame();
    safety_heartbeat(HB_VISION);   /* 收到帧才喂 */
}
```

相机没接 / 没上电 / 烧录后还没重启时，视觉心跳恒为 0 → 同样 2 秒后锁死。
而"链路上没有帧"本来就有专门的判据（`LINK_TIMEOUT` 分级 + 上车宽限期）。

**修复**：心跳移到循环顶部，代表"本任务还在被调度"；有没有帧交给链路超时判据。

### 缺陷 4（间歇性）：心跳时间基准与系统时基不同源

```c
s_hb_last[i] = HAL_GetTick();   /* 改前 */
```

`s_uptime_ms` 由 safety 模块从 0 自增，`HAL_GetTick()` 从 `HAL_Init` 起算。
只要 HSE 锁定耗时超过 1 ms，`HAL_GetTick()` 就大于 `s_uptime_ms`，随后
`s_uptime_ms - s_hb_last[i]` 按无符号运算下溢成 `0xFFFFFFxx`，直接越过 2 s 门限。

**修复**：统一用 `s_uptime_ms` 的基准（初始化时为 0）。
这类 bug 复现与否完全取决于晶振启动快慢，属于最典型的"换块板子就好了"型间歇故障。

### 缺陷 5（致命）：初始化结束停在 `SYS_INIT`，永远进不去 `AUTO`

`safety_init()` 把状态设成 `SYS_INIT` 就返回了。而进入自动模式的条件是：

```c
if (s_state == SYS_IDLE && s_auto_requested && s_link_ever_alive ...)
```

`INIT` 永远不满足 —— 电机不转、状态机不推进、也不报故障。

**修复**：`safety_init()` 末尾显式落入 `SYS_IDLE`（有故障时不允许降级）。

### 缺陷 6（诊断污染）：`uart_link_init()` 重复启动 DMA

`HAL_UART_Receive_DMA()` 内部已经通过 `__HAL_LINKDMA` 关联的 `hdmarx`
调用了 `HAL_DMA_Start_IT`。原代码在它后面又手动启动了一次，第二次必然返回
`HAL_BUSY` —— 于是 `ul_dma_err` 恒为 1，看起来像"DMA 出错"。

**危害不在功能，在诊断**：真出 DMA 故障时这个计数不再有区分度，唯一有效的
信号被废掉了。

## 五、接线（下一步的物理工作）

新固件走 **USART1**，与交付包 README 的引脚表一致：

| 信号 | F407 引脚 | 方向 | OpenMV 引脚 |
|---|---|---|---|
| TX | **PA9**（USART1_TX，AF7） | F407 → OpenMV | **P5**（UART3 RX） |
| RX | **PA10**（USART1_RX，AF7） | F407 ← OpenMV | **P4**（UART3 TX） |
| GND | GND | — | GND |

> ⚠️ **必须交叉**：TX 接对方的 RX。
> ⚠️ **必须共地**，否则电平没有参考，收到的全是乱码。
> ⚠️ 老 GoodDog 固件用的是 **USART3 / PD8 / PD9**。如果机箱里现成的线是接到
> PD8/PD9 的，需要把这两根线挪到 PA9/PA10。挪线前先确认丝印，不要凭颜色。

接好后：

```bash
python _toolchain/verify_f407.py     # 看 vp_frames_ok 是否增长
python _toolchain/monitor_link.py    # 解析 OpenMV 的 [diag] 帧
```
