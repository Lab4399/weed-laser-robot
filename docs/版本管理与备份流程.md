## 一、这套流程要解决什么

| 问题 | 后果 |

流程目标只有一句：**任何时候都能一键回到某个已知良好的状态，并且知道那个状态是什么。**

## 三、版本号规范

`vMAJOR.MINOR.PATCH`，三段含义固定：

| 段位 | 触发条件 | 例子 |
| --- | --- | --- |
| PATCH | 修 bug、调参数、补文档，行为不变 | `v0.1.1` 修正电机死区判定 |
| MINOR | 新增能力，接口向后兼容 | `v0.2.0` 接入 FOMO 检测模型 |
| MAJOR | 架构或硬件平台变更，旧配置不再适用 | `v1.0.0` 换成 H7 + 双目方案 |

**里程碑标签必须对应一个可验证的硬件状态**，标签说明里写清楚"这版能做什么、不能做什么"。例如：

```
v0.1.0  固件源码入库 + 文档齐备 + 双远端打通（未接 FOMO，blob 模式可跑通链路）
```

## 四、分支模型

只有一个长期分支，够用且不容易乱：

| 分支 | 用途 | 规则 |
| --- | --- | --- |
| `main` | 稳定线 | 任何时候 checkout 下来都应该能编译、能烧录 |
| `work/<主题>` | 超过一天的大改动 | 例：`work/fomo-integration`，完成后合并回 main |
| `tag` | 里程碑 | 只打在 main 上，不允许打在临时分支 |

小改动（半小时内能完成）直接提交到 `main`，不必开分支。

## 五、提交规范

```
<type>: <一句话描述>

<正文：为什么这么改，改之前是什么问题>
```

`type` 取以下六种之一：

| type | 含义 |
| --- | --- |
| `feat` | 新增功能或脚本 |
| `fix` | 修复缺陷（含安全漏洞） |
| `docs` | 只改文档 |
| `chore` | 构建、依赖、gitignore 等杂项 |
| `test` | 测试代码 |
| `refactor` | 重构，行为不变 |

三条硬规则：

1. **一次提交只做一件事**——"改文档 + 改固件 + 调参数"必须拆成三次。
2. **正文写"为什么"，不写"改了什么"**——改了什么 git 自己会算。
3. **安全相关修复必须在正文里点明后果**，例如 L298N 那次：不修则 safety 判故障后电机继续转。

## 六、三种日常场景

### A. 日常小改动（最高频）

```powershell
.\tools\backup.ps1 "fix: 修正 motor 死区判定"
```

### B. 里程碑（阶段完成、能上实物验证）

```powershell
.\tools\backup.ps1 "feat: 接入 FOMO 检测并跑通闭环" -Tag v0.2.0 -Both
```

`-Both` 会同时推 GitHub 和 Gitee，双保险。

### C. 出问题了要回到已知良好状态

```powershell
git log --oneline --decorate          # 看有哪些标签和提交
git checkout v0.1.0 -- 相对路径/文件   # 只回退某个文件
git revert <commit>                   # 撤销某次提交（保留历史，推荐）
git reset --hard v0.1.0               # 整体回退（危险，只在本地未推送时用）
```

## 七、一键脚本说明

位置：`tools/backup.ps1`（配套 `tools/backup.bat` 可双击运行）

| 参数 | 说明 |
| --- | --- |
| `-Message` / 位置参数 | 提交信息，省略则交互式询问 |
| `-Tag vX.Y.Z` | 打注解标签并随推送带走 |
| `-Both` | 同时推 Gitee（默认只推 GitHub） |
| `-DryRun` | 只跑预检并列出将提交的内容，不动仓库 |

脚本内置 5 项预检，任何一项不通过都会 `git reset` 撤销暂存并退出：

1. 是否在仓库根目录、当前分支是否 `main`
2. 单文件 ≥ 50 MB 告警、≥ 100 MB 直接阻断（GitHub 硬限）
3. 密钥扫描：Ark Key / `sk-` / `ghp_` / 私钥 / 明文 password 字段
4. 提交信息非空、格式提示
5. 标签是否已存在（防止重复打版本）

建议先跑一次试运行看效果：

```powershell
.\tools\backup.ps1 -DryRun
```

## 八、什么进仓库，什么不进

| 类别 | 是否入库 | 说明 |
| --- | --- | --- |
| 源码（`.c/.h/.py`） | ✅ | 含 `_f407build/fw/app/` 全部自研固件 |
| 文档（`.md/.html`） | ✅ | docs 与根目录说明 |
| 工具脚本（`_toolchain/`、`tools/`） | ✅ | 能复现实验的都要留 |
| 训练权重（`models/*/best.pt`） | ✅ | 单个约 6 MB，可接受 |
| 固件备份（`.bin` 1 MB） | ✅ | 用于比对芯片内容 |
| 数据集 `datasets/`（410 MB） | ❌ | 可用 `_toolchain/parquet2yolo.py` 重新生成 |
| 训练输出 `runs/` | ❌ | 图表与中间态 |
| 第三方 HAL、CubeMX 生成物 | ❌ | 可由 CubeMX 重新生成 |
| 编译产物 `.o/.elf/.bin` | ❌ | 每次编译重出 |
| `.tflite` 模型 | ⚠️ | 拿到 FOMO 模型后再定：< 10 MB 直接入库，更大则考虑 LFS |

`_f407build/` 的放行规则是精确到 `fw/app/` 一级的，改动 `.gitignore` 时不要写成整目录放行：

```gitignore
_f407build/*
!_f407build/fw
_f407build/fw/*
!_f407build/fw/app
```

## 九、常见问题

**Q：提交时满屏 `LF will be replaced by CRLF` 警告**
A：Windows 换行符转换提示，不影响内容，可以忽略。如需彻底消除，加 `.gitattributes` 统一为 LF。

**Q：`git push` 报 `rejected`**
A：说明远端有新提交（多半是在另一台机器或网页上改过）。先 `git pull --rebase origin main` 再推，不要 `push -f`。

**Q：标签打错了想改**
A：本地 `git tag -d v0.1.0`，远端 `git push origin :refs/tags/v0.1.0`，然后重打。已推送的标签不要随意改，会影响别人。

**Q：误把大文件提交了**
A：如果还没推送，`git reset --soft HEAD~1` 撤回提交、`git rm --cached 大文件`、加进 `.gitignore` 后重提交。已经推送的要用 `git filter-repo` 清理历史，代价较大，所以预检宁可严一点。

**Q：四个副本怎么收敛**
A：只改 `E:` 仓库，改完用 `backup.ps1` 提交推送；需要更新 `D:` 交付件时，从仓库 `git archive` 或直接复制出去，并在副本目录放一个 `本目录为只读快照_请勿直接编辑.txt`。
