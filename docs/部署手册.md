# 部署手册：从训练到单片机烧录

本文覆盖「模型怎么训出来 → 怎么变成能烧进单片机的字节 → 怎么验证是对的」全链路。
面向实验室同学，假设你拿到的是本仓库的干净克隆。

---

## 0. 先搞清一件事：模型有几个，各给谁用

这是本项目最容易踩的坑。仓库里有**两个视觉模型**，四个格式，**不是随便选的**：

| 模型 | 格式 | 跑在哪 | 干什么 | 体积 |
|---|---|---|---|---|
| 杂草**检测** YOLOv8n | `models/best.pt` | PC（Python） | 找出画面里所有作物/杂草的**框** | 6.2 MB |
| 杂草检测 YOLOv8n | `export/weed_det.onnx` | PC（OpenCV DNN） | 同上，**给不想装 PyTorch 的场合** | 12.2 MB |
| 杂草**分类** int8 | `models/weed_cls_c8_int8.tflite` → `.cc/.h` | MCU（C8T6） | 对检测框裁出的贴图判「这是作物还是杂草」 | 14 KB |
| 杂草分类 int8 | `models/weed_cls_int8.tflite` → `.cc/.h` | MCU（Flash 充足） | 同上，96×96 输入 | 35 KB |

**关键约束**：
- `.pt` / `.onnx` **单片机跑不了**，只能 PC。
- `.cc` / `.h` 是 **C 数组**，只能单片机。
- **只有 `.cc`/`.h` 是真正要烧进单片机的**。

```
PC 侧：YOLO 检测框 ──裁剪贴图──> int8 分类器 ──> 结论 ──> 传给单片机 ──> 打不打
MCU 侧：只拿到 C 数组，做前向推理，吐一个类别 id
```

## 2. 数据集（一次性，可跳过）

数据集**不在仓库里**（371 MB，太大），用脚本从 HuggingFace 拉：

```bash
python _toolchain\parquet2yolo.py
```

产物：

| 路径 | 内容 |
|---|---|
| `datasets/weed_yolo/` | YOLO 格式检测数据集，1176 图 / 7853 框 |
| `datasets/weed_cls/` | 由检测框裁出的分类贴图，7824 张 |

> ### ⚠️ 类别顺序坑（必读）
> HuggingFace 原始 parquet 是 **`0=weed, 1=crop`**，
> 本项目是 **`0=crop, 1=weed`**。
> `parquet2yolo.py` 里的 `HF2OURS = {0: 1, 1: 0}` 做了重映射。
> **如果你绕过这个脚本自己转数据，必须做同样的映射，否则整套系统会把作物当杂草打。**
>
> 对应地，`laser_strike/config.py` 里 `TARGET_CLASSES = [1]` 指的是 weed。

## 3. 训练检测模型（YOLOv8n）

```bash
python _toolchain\run_train_full.bat
```

或手动：

```bash
yolo detect train data=datasets/weed_yolo/data.yaml model=yolov8n.pt \
    epochs=100 imgsz=640 batch=16 device=0
```

**验证集指标**（本仓库当前结果）：

| | mAP50 | crop mAP50 | weed mAP50 |
|---|---|---|---|
| 原始基线（171 图） | 0.68 | — | — |
| **本模型（1176 图）** | **0.814** | 0.799 | 0.828 |

## 4. 导出部署产物

### 4.1 ONNX（PC 用）

```bash
python _toolchain\deploy_export.py --weights models\weed_det\weights\best.pt --no-simplify
```

`--no-simplify` **必须加**：onnxslim 0.1.98 在本机会段错误（exit 139）。
脚本会自动完成：导出 → onnx.checker 校验 → OpenCV DNN 实测延迟 → 真实图片端到端检测。

期望输出：

```
input   : images  [1, 3, 640, 640]
output  : output0 [1, 6, 8400]      ← 6 = 4 box + 2 classes
CPU 延迟: 中位 ~108 ms → 约 9.3 FPS
```

> **用途**：单片机跑不了 `.pt`，但如果你的部署环境有 OpenCV 而不方便装 PyTorch，
> 用这个 ONNX。只要装了 PyTorch，还是直接用 `.pt`（更快）。

### 4.2 校验导出产物（**别跳过这一步**）

```bash
python _toolchain\verify_export.py
```

它做两件事：

1. **时间戳体检** —— 权重比产物新就报警
2. **数值等价性** —— 同批图上比对 PT 与 ONNX 的原始输出张量

```
  ✅ ONNX 晚于权重 116 小时，顺序正确
  平均最大绝对差 : 0.00534   (阈值 0.02)
  判定：✅ 导出无损，PT 与 ONNX 可互换使用
  CPU 中位延迟 : 95.3 ms   → 约 10.5 FPS
```

> ### ⚠️ 为什么必须校验
> YOLO 训练是一轮轮保存 `best.pt` 的，而 ONNX 导出是一个**独立的手工步骤**。
> 只要中间改过权重、或忘了重导，磁盘上就会出现
> 「`export/weed_det.onnx` 比 `best.pt` 旧」的状态 ——
> 而 ONNX 照样能正常加载、正常推理、正常出检测框，**没有任何报错**，
> 只是精度 quietly 停留在旧模型上。这是最难自己发现的一类问题。
>
> 本仓库就真实踩过一次：ONNX 是 10-11 22:07 导出的，
> 而最终权重是 10-11 23:49 训出来的，产物落后了一整个训练轮次。
>
> 另外注意：**别用 GPU 跑完整 val 来做这件事**。ONNX 的 CPU 推理很慢，
> 176 张图要十几分钟，而且只看 mAP 根本看不出「导出的是哪个权重」。
> 直接比对原始输出张量，6 张图 30 秒搞定。

## 5. 【最重要】类别失衡：为什么不能直接训

从检测框裁出的贴图**严重失衡**：

| 划分 | crop | weed | 比例 |
|---|---|---|---|
| train | 371 | 6380 | **1 : 17** |
| val | 35 | 1038 | **1 : 30** |

如果用原始 `train_cls_int8.py` 直接训，会得到一个**看起来很棒、实际很危险**的模型：

| 模型 | weed 召回 | crop 召回 | 误打作物 | 漏打杂草 | 平衡准确率 |
|---|---|---|---|---|---|
| 交付包旧模型 | 80.5% | 85.7% | 14.3% | 19.5% | 83.1% |
| 原脚本直训 | **99.8%** | 65.7% | **34.3%** | 0.2% | 82.8% |
| **加权训练（推荐）** | 98.9% | 77.1% | **22.9%** | 1.1% | **88.0%** |

看第一行和第二行：weed 召回从 80.5% 冲到 99.8%，**看着像巨大提升**，
但代价是**误打作物率翻倍到 34.3%** —— 三分之一的作物会被激光打坏。
平衡准确率 82.8% vs 旧模型 83.1%，**等于没提升，只是把错误从"漏打杂草"搬到了"打坏作物"**。

> ### 评估只看整体 accuracy 会被骗
> 30:1 失衡下，模型把**所有东西都判成 weed** 也能拿到 96.7% 准确率。
> **必须看逐类指标**：
> ```bash
> python _toolchain\eval_cls_int8.py --model models\weed_cls_c8_int8.tflite
> ```
> 它会输出混淆矩阵、逐类召回、误打作物率、漏打杂草率、平衡准确率。

**解法**（已实现在 `train_cls_int8_balanced.py`）：
1. `class_weight` = 样本数反比（crop 权重 9.1，weed 0.53）
2. 少数类水平翻转增广（仅 train 集，371 → 742）

模型结构、量化方式、输出路径、C 符号名**全部不变**，只改训练侧，固件无需适配。

## 6. 【最容易翻车】C 符号名契约

`tflite_to_cc.py` 生成的 `.h` 里的**符号名必须与固件一致**，否则**编译期就失败**。

正确对应关系：

| 文件 | 符号名 |
|---|---|
| `weed_cls_int8.cc/.h` | `g_weed_cls_model` |
| `weed_cls_c8_int8.cc/.h` | **`g_weed_cls_c8_model`**（注意：没有 `_int8`） |
| `weed_cls_c8rgb_int8.cc/.h` | `g_weed_cls_c8rgb_model` |

> 这就是为什么 `tflite_to_cc.py` 里要用**显式映射表** `SYMBOLS`，
> 而**不要**按文件名自动推导 —— 按名字推导会得出 `g_weed_cls_c8_int8_model`，
> 和原训练脚本 `train_cls_int8_c8.py` 用的 `g_weed_cls_c8_model` 对不上，固件链接失败。

**每次重新生成后，请复验**：

```bash
grep -h "extern const" models\weed_cls_c8_int8.h
# 期望：extern const unsigned char g_weed_cls_c8_model[];
```

### 内存占用（决定能不能上 C8T6）

| 模型 | 输入 | Flash | 峰值张量 | C8T6 (64K Flash / 20K SRAM) |
|---|---|---|---|---|
| `weed_cls_c8_int8` | 48×48 | 14.0 KB | 9.2 KB | ✅ 可用 |
| `weed_cls_int8` | 96×96 | 34.7 KB | **144 KB** | ❌ 撑爆 |

**C8T6 请用 48×48 版本。**

### 反直觉发现：48×48 反而更准

48×48 的平衡准确率 **88.0%**，96×96 只有 **85.7%**。原因是 crop 只有 371 个样本，
输入维度越大越容易过拟合少数类。**不是模型越大越好。**

### 7.3 整机联调

`laser_strike/` 是 **PC 端 Python**（用 `.pt`），单片机是 `laser_strike/arduino/laser_gimbal.ino`
（只负责云台伺服 + 激光开关，通过串口接收指令）。串口参数：

| 设备 | 端口 | 波特率 |
|---|---|---|
| 激光云台 | `COM3` | 115200 |
| Good Dog 底盘 | `COM4` | 115200 |

联调顺序：
1. 先只测云台（不接激光），确认角度控制方向与限幅正常
2. 再串 `GOOD_DOG` 测行走
3. 最后接激光，且**先在 config 里把 `LASER_HOLD_SEC` 调小**（如 0.2），确认无误触发再调回 1.0

## 9. 故障速查

| 症状 | 原因 | 处理 |
|---|---|---|
| `onnxslim` 段错误 exit 139 | onnxslim 0.1.98 崩溃 | 加 `--no-simplify` |
| `import tensorflow` / `onnxruntime` 段错误 | **GPU 被训练占满时 DLL 冲突** | 等训练结束，GPU 空闲后自动恢复（不是环境坏了） |
| 固件链接报 undefined symbol | C 符号名对不上 | 见第 6 节，用 `SYMBOLS` 映射表 |
| C8T6 编译 OOM | 用了 96×96 模型 | 换 48×48 版本 |
| 评估报 `Got 256 but expected 1` | 批量推理但模型 batch 固化为 1 | 逐张推理 |
| 评估报 `Got 96 but expected 48` | 硬编码了输入尺寸 | 从 `.tflite` 读 `get_input_details()` |
| 模型把作物当杂草打 | 类别顺序错 | 检查 `HF2OURS` 重映射 |
| 换了权重但精度没变 | ONNX 没重导，产物比权重旧 | `python _toolchain\verify_export.py` |
| accuracy 98% 但效果很差 | 类别失衡 | 看逐类指标，见第 5 节 |
| pip 403 / `from versions: none` | 沙箱代理拦截 | `env -u http_proxy -u https_proxy python -m pip ...` |
